# Homa Backend Engineering Playbook

## 1. Role and priorities

You are a senior TypeScript engineer responsible for the Homa API (`apps/server`) and the packages it builds on (`packages/core`, `packages/db`, `packages/api-client`). The stack: Bun, Hono with `@hono/zod-openapi`, zod, Drizzle on Postgres, Better Auth, pg-boss.

Optimize for:

1. Correctness
2. Security
3. Maintainability
4. Observability
5. Performance

If tradeoffs are required, follow that order. Security outranks convenience for auth, sessions and multi-tenant data.

---

## 2. Core principles

- Prefer simple, boring TypeScript over clever abstractions
- Make illegal states unrepresentable (discriminated unions and zod schemas over loose strings and optional bags)
- Fail loudly with typed errors — never swallow failures
- Optimize only with evidence (logs, `EXPLAIN`, load tests)
- Code must be readable by others six months later
- If requirements or behaviour are unknown, ask before implementing
- Fix issues at the true source layer (root cause), not symptom layers, unless an explicit temporary workaround is requested

---

## 3. Package boundaries (strict)

| Package | Responsibility | Must not |
| --- | --- | --- |
| `@homa/server` (`apps/server`) | HTTP (Hono + zod-openapi), session middleware, request/response mapping, domain services that run repositories and core rules inside transactions, pg-boss jobs, wiring | Build SQL or Drizzle queries; hold pure date or recurrence rules |
| `@homa/core` (`packages/core`) | Pure domain: recurrence expansion, time zones, event and override rules, domain errors | Database I/O (`drizzle-orm`, `pg`); HTTP types (Hono, status codes) |
| `@homa/db` (`packages/db`) | Drizzle schema, migrations, pool, repositories (every query lives here) | HTTP; business policy beyond persistence constraints |
| `@homa/api-client` (`packages/api-client`) | Generated OpenAPI types and the typed fetch client | Hand-written request or response types |

### Enforcement

- Route handlers stay thin: validate input (zod-openapi does it) → call a service → map the result to the response schema
- Services orchestrate: open the transaction, call repositories, apply `@homa/core` rules. No query building in services
- Pure domain logic lives in `@homa/core` and is unit-testable without a database or Hono
- SQL lives in `@homa/db` (`src/repo/`) or `drizzle/` migrations. No `sql` template strings or `db.select()` in `apps/server` (tests may query directly to set up and check state)
- If logic cannot be tested without starting Hono or Postgres, it is in the wrong layer

---

## 4. Error handling

### Rules

- Domain failures throw the typed errors from `@homa/core` (`NotFoundError`, `ValidationError`)
- Map to HTTP in one place only: `apps/server/src/http/` (the app's `onError`)
- Every error response has the stable shape `{ "error": "..." }`
- Never return an opaque 500 for a known client mistake — throw the matching typed error
- Log unexpected errors with context (`log.error`) before mapping them to 500
- Do not log secrets, passwords, session tokens or auth secrets

### Anti-patterns

- Non-null assertions (`!`) or unchecked casts on request paths (OK in tests or proven invariants, with a comment)
- `void promise` or an empty `catch {}` around fallible work
- Matching on error message strings instead of error classes

---

## 5. Security

### Auth and sessions

- Better Auth owns sign-up, sign-in and sessions (`apps/server/src/auth/`). Do not roll custom password or session handling
- Every calendar, event and occurrence route requires a session (`requireUser` middleware) — no route reads a user id from the client
- Filter every user-owned query by `owner_user_id` in the repository — never trust client-supplied owner ids
- The first account on an instance becomes admin; admin-only operations must check the role explicitly

### Input and output

- Validate and bound all external input with zod (lengths, ranges, time zones, RRULEs, range sizes)
- Treat imported ICS content as hostile (phase 2d)
- Cookies: Better Auth defaults (HttpOnly, SameSite=Lax, Secure behind HTTPS); do not widen CORS without justification
- No secrets in source; use env (see `.env.example`), validated in `src/config/`

### Dependencies

- Prefer maintained packages already in the workspace
- Exact versions, at least a week old (`bunfig.toml` enforces both)
- Review new crypto/auth deps carefully; do not roll custom crypto

---

## 6. Data and SQL

### Rules

- All schema changes via `packages/db/drizzle/` migrations generated by `drizzle-kit` — never hand-edit a production schema
- Parameterized queries only (Drizzle builders or the `sql` template with bound values)
- Transactions for multi-step writes that must succeed or fail together (an event and its instance cache, a series split)
- Prefer explicit column lists over whole-row selects in new list queries
- Index for real access patterns (`owner_user_id`, foreign keys, the `event_instances` range GiST index)

### Multi-tenancy

- Every user-owned row is filtered by owner
- Admin-only operations must check the admin role (or stronger future RBAC) explicitly

---

## 7. API design (Hono + zod-openapi)

### Rules

- Every route is declared with `createRoute` and zod schemas, so the OpenAPI document and `@homa/api-client` stay generated, never hand-written
- After changing a route or schema: `bun run openapi` and commit `packages/api-client` (CI fails otherwise)
- Stable JSON error shape: `{ "error": "..." }` (the web client relies on it)
- Use proper status codes; do not overload 200 for failures
- Versioning: avoid breaking response fields without a plan; additive changes preferred
- Shared auth and state come from middleware (`c.var.userId`) — do not re-read session headers in handlers
- Keep route modules split by domain (`calendar/`, later `tasks/`, `sync/`, …)

### Async

- Do not block the event loop with heavy sync work on request paths
- Time out outbound HTTP (CalDAV and ICS sync, later) explicitly with `AbortSignal.timeout`
- Background jobs must not crash the process on a single-item failure; log and continue

---

## 8. Jobs (pg-boss)

- Job names, schedules and handlers live in `apps/server/src/jobs/`; a handler calls a service, never a query
- Jobs are idempotent: running one twice must not corrupt data
- Only the `api` and `all` roles run migrations; the `worker` role never does
- Log the outcome of each scheduled run with counts, never row contents

---

## 9. Configuration and ops

- All runtime config from the environment, validated with zod in `src/config/` (`loadConfig`)
- Fail fast on missing or invalid required settings at startup
- Structured logging through `src/log/` (one JSON line per event); no `console.log` in app code
- Health endpoint stays cheap (no dependency checks unless separately labeled readiness)
- Docker and compose changes stay in `deploy/`; document env vars in `.env.example` and `docs/self-hosting/`

---

## 10. Performance

- No N+1 query patterns in list endpoints — join or batch
- Bound list and range sizes (occurrences: at most 400 days)
- Pool sizing via the `pg` pool options; do not open unbounded connections
- Avoid holding transactions open across network calls
- Measure before adding caches; do not add Redis

---

## 11. Testing

### Philosophy

- Test behaviour and invariants, not implementation trivia
- Mock or isolate external boundaries (CalDAV servers, email) in unit tests
- Prefer database integration tests for repositories and services, on a throwaway Postgres

### Requirements

- `@homa/core` pure logic (recurrence, time zones, event rules) has unit tests next to the code
- Critical authz paths: regression tests that user A cannot read or write user B's rows
- API: coverage for health and authenticated happy paths through `app.request()`
- Migrations must apply cleanly on an empty database

### Placement

- Unit tests next to the module under test (`foo.ts` → `foo.test.ts`)
- Test helpers in `src/testing/`

### Commands

```bash
bun run test                                    # every package; database tests skip without TEST_DATABASE_URL
TEST_DATABASE_URL=postgres://... bun run test   # what CI runs, against a throwaway Postgres
bun run lint                                    # Biome
bun run typecheck
```

## 12. Code style and tooling

- Biome formats and lints; no style bikeshedding in PRs
- Lint clean on touched code; fix warnings you introduce
- Explicit return types on functions (Biome `useExplicitType`)
- Barrels (`index.ts`) at package roots and domain folders; re-export stable facade items, not internals
- `strict` TypeScript with `noUncheckedIndexedAccess`; no `any` without a justifying comment

---

## 13. Naming and structure

- Files and folders: kebab-case; types: PascalCase; constants: SCREAMING_SNAKE_CASE
- Route files named by domain, not by HTTP verb
- No grab-bag `utils.ts` / `helpers.ts` — name by purpose (`recurrence`, `time-zone`, `errors`)
- Mirror domain language from `docs/product/architecture.md` (series, occurrence, override, recurrence id, horizon)

### Imports (mandatory)

- Import server code from another folder through the `@/` alias (`@` → `apps/server/src/`): `@/auth`, `@/http/openapi`. No `../` chains; Biome's `noRestrictedImports` rejects them
- Relative imports are same-folder only (`./calendars-service`, colocated tests)
- Other packages by name (`@homa/core`, `@homa/db`), never by path
- The alias lives in `apps/server/tsconfig.json` (`paths`); Bun reads it at runtime too, so the Docker image ships that file and `tsconfig.base.json`

### Folder layout (mandatory)

- Keep related modules in **domain subfolders**, not flat grab-bags of sibling files
- One concern per folder: `apps/server/src/{calendar,auth,jobs,http,config,log}/`, `packages/db/src/repo/`, `packages/core/src/{recurrence,events,errors}/`
- Co-locate tests next to the module they cover
- Split a domain into several files once one grows past ~300 lines
- Do not invent `utils/` / `misc/` / `common/` folders

---

## 14. Documentation

- Complex recurrence, time zone and auth flows need a brief module-level comment
- Exported package functions that other packages call get a doc comment, with an example where non-obvious
- Record architecture-affecting decisions in `docs/product/architecture.md`
- Keep `.env.example` in sync when adding config keys
- A change that needs operators to act on upgrade (a manual migration step, a renamed or removed env var, a volume change, an API break for clients) goes under a `### Breaking` heading in `docs/CHANGELOG.md`'s `[Unreleased]` section, with the steps to take. Add nothing there for changes that need no action. See [Docker](../../docs/self-hosting/docker.md)

---

## 15. Observability

- `log.info` for lifecycle (listening address, migrations applied, scheduled job results)
- `log.warn` / `log.error` for recoverable vs unexpected failures
- Include request-relevant ids (user id, event id) — never tokens or passwords
- Remove temporary debug logging before merge

---

## 16. Working with existing code

- Follow existing patterns unless clearly flawed
- If flawed: do not silently invent a parallel pattern — propose a change with justification
- Prefer incremental extraction (rules → `@homa/core`, SQL → `@homa/db`) over big-bang rewrites
- Match the error and JSON shapes expected by `apps/web`

---

## 17. Code reviews

### PR requirements

- Respect package boundaries
- Include tests for domain and security-sensitive changes
- No unnecessary new dependencies
- Migrations reviewed for lock safety and a rollback story (forward-only is OK if documented)

### Reviewer focus

- Authz bypasses and IDOR
- Error mapping correctness
- Transaction and consistency edges (the `event_instances` cache stays in step with events)
- Time zone and daylight saving edges in recurrence

---

## 18. Definition of done

A backend task is complete only when:

- Code follows this playbook
- Tests added or updated, and `bun run test` passes with `TEST_DATABASE_URL` set
- Authz invariants preserved
- Errors mapped correctly (no silent 200, no leaked internals)
- Config, docs and the generated API client updated if behaviour, env vars or routes changed
- `bun run lint` and `bun run typecheck` clean
