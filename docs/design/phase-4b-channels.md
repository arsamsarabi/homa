# Phase 4b: notification channels (email, ntfy, Gotify, webhooks)

Status: built in the `phase-4b-channels` PR, 2026-11-20, on top of Phase 4a (`docs/design/phase-4a-reminders.md`).

## Scope

- Channels a user adds in Settings, beside the in-app bell (always on) and web push (per browser, from 4a): **email** over the instance's SMTP server, **ntfy**, **Gotify** and **webhooks** (a signed JSON POST).
- Each channel chooses which reminder kinds it gets: event reminders, standalone reminders, or both.
- A "Send test" button per channel, and the channel's last error in Settings when it keeps failing.
- Out of scope: Matrix, Telegram, Slack-specific formats (a webhook covers them through a bridge), digest emails, per-calendar channel choice.

## Data model

| Table | Columns | Notes |
| --- | --- | --- |
| `notification_channels` | `owner_user_id`, `kind` (`email`, `ntfy`, `gotify`, `webhook`), `name`, `enabled`, `reminder_kinds` (text[]: `event`, `standalone`), `config` (AES-256-GCM ciphertext, null for email), `consecutive_failures`, `last_error`, `last_error_at`, `last_sent_at` | One row per channel. At most 10 per user |

`config` holds everything a channel needs to send, encrypted with `HOMA_ENCRYPTION_KEY` the way connections are (`encryptCredentials`, with `channel:{id}` as the row id so a ciphertext can't move between rows or tables):

| Kind | Config |
| --- | --- |
| `email` | none: it always goes to the account's own address, so Homa can't be used to mail strangers |
| `ntfy` | `server` (default `https://ntfy.sh`), `topic`, optional access `token` |
| `gotify` | `server`, app `token` |
| `webhook` | `url`, `secret` (32 random bytes, base64url, generated by Homa) |

Topics and webhook URLs count as secrets too: on ntfy.sh the topic is the password, and Discord or Slack webhook URLs carry a token. The API returns a webhook's host only, and never returns tokens or secrets after creation. ntfy's server and topic and Gotify's server are returned so they can be edited.

Without `HOMA_ENCRYPTION_KEY`, adding an ntfy, Gotify or webhook channel answers 503 with the reason (email works). A server that has such channels but lost its key still starts; those deliveries fail with "HOMA_ENCRYPTION_KEY is not set".

Deliveries reuse 4a's `notification_deliveries`. The `channel` column is `push` or `channel:{id}`, unique per notification, so each channel retries on its own.

## Job flow

1. When a notification is created or comes back from snooze, `deliveriesFor` queues one delivery per enabled channel of its owner whose `reminder_kinds` include the notification's kind (`event` if it has an event, else `standalone`), plus `push` if the user has a push subscription.
2. The `reminders.deliver` job sends them as before: a 5-minute lease, then sent, or retried after 1, 2, 4 … minutes, and failed after 8 tries. A channel that was deleted or disabled since then fails its delivery without sending.
3. Each send records the result on the channel: success clears `consecutive_failures` and `last_error` and sets `last_sent_at`; a failure increments the counter and stores the error. Settings shows a channel as failing at 3 consecutive failures, with its last error.

**Errors and retries.** A network error, a timeout (10 seconds), 429 or 5xx is retriable. Other 4xx answers, redirects (not followed) and refused addresses fail the delivery at once. SMTP: connection errors and 4xx replies retry; 5xx replies fail.

## Senders

- **Email** (`nodemailer` 10.5.0): `HOMA_SMTP_URL` (`smtp://user:pass@host:587` for STARTTLS, `smtps://…:465` for TLS) and `HOMA_MAIL_FROM` (`Homa <homa@example.com>`). Both or neither. Without them the email option is hidden in Settings and existing email channels fail with "email is not set up on this server". The message: subject `Reminder: {title}`, a plain-text body with the time in the user's home zone and locale, and a link to `HOMA_URL`. This is the first mail Homa sends.
- **ntfy**: `POST {server}` with JSON `{ topic, title, message, click: HOMA_URL, tags: ["bell"] }`, and `Authorization: Bearer {token}` when there is a token.
- **Gotify**: `POST {server}/message` with header `X-Gotify-Key: {token}` and JSON `{ title, message, priority: 5, extras: { "client::notification": { click: { url: HOMA_URL } } } }`.
- **Webhook**: `POST {url}` with JSON `{ type: "reminder" | "test", id, title, startAt, allDay, kind, fireAt, url }` and headers `X-Homa-Timestamp` (Unix seconds) and `X-Homa-Signature: sha256={hex HMAC-SHA256 of "{timestamp}.{body}" with the secret}`. Receivers should check the signature and reject timestamps more than 5 minutes old. `docs/self-hosting/notifications.md` has a verification snippet.

**SSRF.** ntfy, Gotify and webhook addresses must be `https` and resolve to public addresses only, checked when saved and again before each send (`assertPublicHost`). `HOMA_NOTIFY_ALLOW_PRIVATE_NETWORKS=true` allows `http` and loopback, private and link-local addresses, for a self-hosted ntfy or Gotify on the LAN. Addresses with a user name or password are refused (use the token fields). The SMTP server is the admin's own setting and isn't checked.

## API

- `GET /api/notification-channels` answers `{ items, email }`, where `email` says whether SMTP is set up.
- `POST /api/notification-channels` with `{ kind, name, reminderKinds, ...config }` creates one. A webhook's answer includes its `secret`, the only time it is shown.
- `PATCH /api/notification-channels/{id}` changes `name`, `enabled`, `reminderKinds` or the config fields. Omitted secret fields are kept; ntfy's `token: null` removes it. A webhook's `rotateSecret: true` makes a new secret and returns it.
- `DELETE /api/notification-channels/{id}`.
- `POST /api/notification-channels/{id}/test` sends a test message now and answers `{ ok, error }`. It records the result like a delivery.

Another user's channel is a 404. The JSON export leaves channels out, since their config is secret.

## Web

Settings gets a "Notification channels" section under the push one: the list (name, kind, which reminders, enabled switch, failing badge with the last error), and a drawer to add or edit one with fields per kind, the reminder-kind checkboxes, "Send test" and delete. A new webhook's secret is shown once with a copy button. The kind picker is a native select.

## Limits

| What | Limit |
| --- | --- |
| Channels per user | 10 |
| Name | 100 characters |
| URLs | 2,000 characters |
| Send timeout | 10 seconds |
| Tries | 8 (shared with push), then failed |
| "Failing" in Settings | 3 consecutive failures |

## Open questions

- Per-kind choice for web push (it gets every kind today; the browser opt-in is the switch).
- ntfy action buttons for snooze and done would need a token in the message; left out.
- DNS rebinding: the address is checked and then fetched separately, as for calendar feeds. Pinning the resolved address would close that gap.
- An email address other than the account's, with a confirmation link.
